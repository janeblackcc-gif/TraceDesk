# TraceDesk 设计审查与未决事项

## 1. 一致性审查结论

### 需求 → 任务 → 验收
01 号 `PC-01~20` 均在 06 号映射到 `T-*`，并在 08 号 `FA-*` 有可判定场景。没有把“优化检索/完善权限/上线”留成未展开大任务。

### 数据模型 → API/权限
- workspace/KB membership 能支撑所有文档/query/source/trace/job/eval 的服务端授权；
- `auth_version/permission_epoch/data_epoch` 支撑撤权与数据切换竞争；
- logical document + immutable revision + active/desired 指针支撑替换不打断旧版；
- index generation 与 model profile 分离，能识别模型 digest/维度变化；
- legacy ID 字段能解释旧引用而不把旧 ID 重新指向新内容。

### 任务状态 → 崩溃/取消/替换
状态机覆盖 queued/running/retry_wait/succeeded/failed/cancelled/superseded；lease 过期可重领。最终提交 CAS 同时检查 lease、cancel、deleted、desired revision、manifest，因此“旧任务晚完成”不会复活数据。

### 迁移 → 恢复
不把 Alembic 当数据备份。schema migration 与 SQLite data migration 分开；源库只读保留；大迁移 checkpoint；不可逆失败用备份恢复。旧原文件本来就未保存，因此迁移明确标 `source_file_available=false`，不伪造原 PDF。

### 日志 → 敏感资料
普通日志禁止 question/chunk/quote/token/session/password/DB URL；业务 trace 受 ACL/retention 控制。审计只存动作和资源元数据。仍需在编码时做自动日志扫描，不能只靠约定。

### 质量/性能 → 资源
当前 8GB GPU 只支持“生成并发1”的默认起点；P95 30s 是试点预算，不是已测 SLA。若更强模型需要更大 GPU，成本由 M6 质量收益和 M8 容量报告共同决定。

## 2. 反例检查

1. **用户 A 猜到 B 的 chunk UUID**：source endpoint 先查 KB 权限，默认 404，不返回 filename/page。
2. **Editor 上传 v2，v1 index job 最后完成**：desired_revision 已变，CAS 失败，v1 job superseded。
3. **删除文档时模型正在生成**：data_epoch/permission recheck 失败，生成结果丢弃，删除后 source 不可取。
4. **worker 在 embedding 第 90% 崩溃**：generation 非 active；lease 过期重领；重复 batch 写以 `(generation_id,chunk_id)` 幂等。
5. **取消和完成同一毫秒竞争**：最终事务条件更新决定唯一终态；取消请求不能在 commit 后反向声称已取消。
6. **模型 tag 不变但 digest 变**：model_profile 不同；旧 generation 不满足新 profile。
7. **恢复了旧备份，任务 lease 仍显示 running**：恢复启动流程统一让过期 lease 可重领，不把 wall clock 中断任务当成功。
8. **旧导出引用一个已删除 legacy ID**：返回 410/历史元数据，不指向同名新 revision。
9. **管理员删除用户后，旧 session 仍在浏览器**：auth_version/status 检查使 session 无效。
10. **解析器 hang/内存暴涨**：子进程限额终止；Web/其他 worker 不受同进程拖累。
11. **日志 debug 模式误打 prompt**：结构化 logger 白名单 + CI 敏感 fixture 扫描；生产禁止任意 request body logging。
12. **HNSW 提速但召回下降**：只有 exact vs ANN 在冻结集通过质量门槛才启用。
13. **OCR 看似提高覆盖但拖慢所有文档**：OCR 仅对检测为无文本/扫描的文档触发，并先有真实比例证据。
14. **holdout 失败后开发者修改 gold**：dataset hash 变化，原 run 保留；修改必须创建新 dataset version 并说明原因。
15. **CI 179+ 全绿但真实用户仍失败**：M9 独立门禁，工程绿不能关闭产品验收。

## 3. 仍待确认的问题

### A. 阻塞架构选择

| 问题 | 当前默认 | 依据 | 改变时影响 | 最迟节点 |
|---|---|---|---|---|
| 是否公网/跨组织 | 单组织内网 | 原 PRD 主场景、小团队；当前无多租户 | TLS/WAF/SSO/滥用/合规/HA/容量 | M1结束 |
| 规模是否>50k chunk/5并发 | 否 | 当前数据规模与8GB GPU起点 | ANN、对象存储、模型拆机、DB HA | M4前 |
| 是否已有 OIDC/SSO | 无，先本地账号 | 未提供组织 IdP | T-020/021 替换为 OIDC adapter | M2开工前 |

若答案改变，只替换局部 ADR/任务，不重写整套方案。

### C. 编码时可确认

- UUIDv4 vs UUIDv7：默认 UUIDv7（若依赖/DB实现稳定），否则 UUIDv4；不影响业务语义。
- cursor token 编码：默认服务端签名 opaque token。
- parse timeout 120s、mem1.5GB、temp2GB：T-034/M8 校准。
- 分页 50/200、job lease30s/heartbeat10s：T-025/M8 校准。
- Prometheus/OTel 具体 exporter：先标准接口，部署环境决定 exporter。
- 反向代理实现（Caddy/Nginx/组织网关）：不改变应用授权；由部署环境选择并锁版本。
- OCR 引擎：只有触发 OCR 决策后再选，不提前绑定。

## 4. 已采用但尚未验证的假设

1. 小团队愿意维护一台 Linux/Compose 主机；

6. 本地账号在无组织 IdP 时可接受；

每条都不是事实。对应证据在 M6/M8/M9 补齐。

1. **覆盖剩余全部阶段？** 是：M0–M9，数据、权限、任务、检索质量、部署、恢复、容量、真实试用均有任务。

5. **有真实质量、性能、运维、用户验收？** 是：05、07、08、T-060~081。
6. **假设与未验证项明确？** 是：本文件第3–5节；未把历史浏览器/模型记录说成本次重跑。
7. **现在即可启动的首项任务？** 是：**T-001**，依赖已满足；随后 T-002、T-010。无需等待真实用户或购买资源。

## 7. 设计审查结论

在默认“单组织内部小团队、≤50k chunk、≤5 并发、单机 Linux + 本地模型”假设下，本套设计可进入 M0/M1 实施。  
**尚不能批准真实试点**：真实资料授权、用户、正式质量阈值和目标部署资源未冻结；这些最迟按上表节点关闭。  
**尚不能批准正式产品交付**：必须先通过 08 号工程/质量门禁与 M9 真实试用。
