# TraceDesk 部署、运维、安全与容量

## 1. 环境分层

### 开发验证
Windows 11 + PowerShell 7 + Python 3.13 + RTX 4060 Ti 8GB。允许直接运行 FastAPI/Ollama，用于代码、模型和 UI 调试。**不作为多人生产环境**。

PowerShell 7：
```powershell
py -3.13 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-lock.txt
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe scripts\start.py --check
```

### 默认生产
Linux x86_64 + Docker Engine/Compose。服务：reverse proxy、web、parse worker、index worker、PostgreSQL+pgvector；Ollama 同机或受控内网 GPU 主机。所有镜像按 tag + digest 固定。

Linux：
```bash
cp .env.production.example .env.production
docker compose --env-file .env.production pull
docker compose --env-file .env.production run --rm migrate alembic upgrade head
docker compose --env-file .env.production up -d
docker compose ps
curl -fsS https://tracedesk.example.internal/readyz
```
域名/证书是示例变量，实施时由真实内网域名替换。

## 2. 默认版本基线

- PostgreSQL 18.6；
- pgvector 0.8.6；
- SQLAlchemy 2.0.52；
- Alembic 1.19.2；
- 当前 FastAPI/Uvicorn 版本先保持 RC2 兼容，升级另开 PR；
- Ollama 0.33.3 是当前已测起点，部署前检查官方稳定版本与 Qwen structured output 兼容；不在业务 PR 顺手升级；
- pip-audit 2.10.1 用于 Python 已知漏洞审计。

## 3. Compose 约束

- PostgreSQL 必须有 healthcheck；web/worker `depends_on: condition: service_healthy`。
- DB、originals、backup staging 使用持久卷；临时 parse 使用 tmpfs/受限临时目录。
- web/worker 以非 root 用户运行；容器 root filesystem 尽量 read-only，仅挂需要写的目录。
- restart policy `unless-stopped` 或受控 on-failure；迁移容器必须成功后 web 才可升级。
- Compose 不是 HA。主机故障恢复依赖备份；若要求 HA，另立 ADR。

Docker 官方文档说明 Compose 仅“启动”依赖并不等于 ready，需 healthcheck + `service_healthy`；本方案据此实现。

## 4. 配置与密钥

配置分三类：
1. 非敏感：端口、limits、model tags、retention，环境变量/配置文件；
2. 敏感：DB password、bootstrap token、session signing/pepper（若使用），只通过 Docker secrets/受限文件/组织 secret store；
3. 运行时业务数据：用户资料、原文，不放环境变量和日志。

`.env` 不入仓。启动时：
- 未知 `TRACEDESK_*` 变量直接失败，延续 RC2 的 typo protection；
- 生产模式禁止默认密码；
- bootstrap token 只在首 admin 创建前存在，用后撤销；
- 日志永不打印完整配置字典。

## 5. 认证、传输和网络

- reverse proxy 终止 TLS；HTTP 重定向 HTTPS；HSTS 仅在域名和证书稳定后启用。
- Web 仅暴露 443；PostgreSQL、worker 不对用户网段暴露。
- Ollama 若远端，只允许受控地址；禁止把任意 URL 当 provider，防 SSRF。
- Cookie Secure/HttpOnly/SameSite；写请求 Origin+CSRF。
- 默认本地账号 Argon2id；若组织 OIDC 可替换认证，但 ACL 仍在 TraceDesk。
- 失败登录、权限变更、敏感导出进入审计。

## 6. 文件处理安全

依据 OWASP File Upload：
- allowlist `.md/.txt/.pdf`；
- 不信任 Content-Type，结合扩展、magic/signature、解析结果；
- 存储名系统生成，不使用用户路径；
- 文件在 webroot 外；
- 上传大小、页数、解析字符、临时空间、任务队列均有限；
- parser 子进程无网络、低权限、受 cgroup/容器限制；
- 可选杀毒扫描只作为 defense-in-depth，不把“扫描通过”当安全证明；
- 原文件下载走授权 API；
- ZIP 默认不支持，避免解压炸弹与路径问题。

## 7. 限流与资源配额

默认：
- query 30/用户/分钟；
- upload 10/用户/分钟；
- 每用户同时 query job 2；
- 每 KB 同时 index 1；
- GPU generation 并发 1（8GB 起点）；
- parse 并发 2；
- query queue 20，parse/index queue 100；
- 单 parse wall 120s、mem 1.5GB、temp 2GB；
- 单模型调用 overall 120s，实际在 M8 校准。

达到上限返回 429 + `Retry-After`。管理员可调，但配置变更写审计。

## 8. 依赖、静态与发布检查

CI 最低顺序：
```bash
python -m pip install -r requirements-lock.txt
python -m pip check
pip-audit --locked   # 若采用PEP751锁文件；否则对锁定requirements审计
mypy app/core app/db app/auth app/authz app/jobs app/services
python -m pytest -q
alembic upgrade head
python scripts/start.py --check
python scripts/acceptance_smoke.py
```

- 已知 high/critical 漏洞默认阻断；无法升级时必须有风险接受、缓解、到期日。
- pip-audit 不等于静态代码安全分析；需配合代码审查和权限测试。
- 新模块逐步开启 mypy strict；不要求一次性给历史所有文件加类型而阻断功能迁移。
- OpenAPI snapshot diff 属于 API breaking-change 门禁。

## 9. 健康、日志、指标与告警

### `/livez`
只表示进程事件循环/线程可响应。DB/Ollama 挂了仍可 live。

### `/readyz`
检查：
- DB 可连接；
- schema revision=head；
- object store 可读写探针；
- job repository 可读；
- 生产配置合法。
Ollama 是否必须 ready 取决于 profile：evidence-only 部署可 ready；RAG-required 部署则模型依赖失败使 ready degraded/false，由部署策略固定。

### 结构化日志
字段：timestamp、level、service、version、request_id、user_id(内部ID)、workspace/kb id、route、status、latency、error_code、job_id。  
禁止：question、chunk text、quote、password、token、session id、DB URL、模型 prompt 全文。业务 query/trace 放受权限控制的 DB 表。

### 指标
- HTTP request count/error/latency；
- auth failures/403/429；
- jobs queued/running/retry/failed/lease expired；
- parse duration/pages/timeout/OOM；
- index chunks/sec、embed batch latency、generation activation；
- retrieval sparse/dense latency；
- model queue/load/prompt eval/generation/timeout；
- query queue_ms/retrieval_ms/generation_ms/total_ms；
- DB pool wait、storage free bytes；
- process CPU/RAM，GPU 由宿主 exporter/采样脚本提供。

### 默认告警
- readyz 连续 3 次失败；
- 5xx >5% 持续5分钟；
- query queue >15 持续5分钟；
- job lease expiry >3/10分钟；
- parse timeout >10%/15分钟；
- 磁盘可用 <15% warning、<8% critical；
- backup 超过 26 小时未成功；
- 质量不是实时 Prometheus 告警，但每个 release 必须跑冻结评测。

## 10. SLO 与测量边界

试点 SLO：
- 可用性 99.0%/月，排除公告维护；
- 非模型 API P95≤500ms；
- evidence 查询 P95≤2s；
- query queue P95≤2s；
- 本地 RAG 总响应 P95≤30s（默认8GB GPU起点）；
- job 最终状态可观察率 100%；
- 权限/版本越界 0。

时延字段必须分：
`queue_ms + retrieval_ms + context_ms + model_wait_ms + generation_ms + citation_ms + serialization_ms = server_total_ms`（允许少量计时重叠但需定义）。  
流式后单独测 TTFT；当前非流式不能宣传首字延迟。

## 11. 数据保留

默认建议：
- 安全 audit：90 天；
- query/trace：30 天，可由用户删除会话但审计元数据独立；
- job attempts：30 天；
- failed parse 临时输出：任务结束即删；错误摘要30天；
- superseded index generation：至少24小时，最多7天；
- soft-deleted document：7天；
- backup：7日+4周。
真实政策必须在 M6/M9 前由数据 owner 确认。

## 12. 备份、恢复、升级

备份集包含：
- PostgreSQL dump/物理备份；
- originals/objects；
- deployment manifest（app image digest、schema revision、pgvector version、model profiles）；
- backup manifest/hash。

恢复必须在**另一目录/卷**演练，不覆盖唯一备份。恢复后执行 ACL、hash、active generation、legacy ID、冻结查询 smoke。

升级：
1. 备份并验证 manifest；
2. `docker compose pull`；
3. migration dry-run/preflight；
4. `migrate` 容器；
5. 新 web/worker；
6. readiness + smoke；
7. 观察窗口；
8. 失败按 runbook 回滚 app 或恢复 backup。
不可逆 schema 使用 expand/contract，不能指望任意 Alembic downgrade 恢复数据。

## 13. 容量测试

必须同时覆盖：
1. 50k chunk 稳态 5 并发 query；
2. 2 个接近上限 PDF parse + query；
3. full reindex + query；
4. 模型断开/重启；
5. worker kill -9；
6. DB 短时重启；
7. queue full；
8. 磁盘接近 warning；
9. 替换/删除与旧任务竞争；
10. 30–60 分钟稳态观察内存/显存是否持续增长。

报告 P50/P95/P99、错误率、queue、CPU/RAM/VRAM、DB/磁盘、索引吞吐，不只报告平均值。

## 14. 扩容触发

- 活跃 chunk >200k 或 exact dense P95 超预算：先 HNSW 消融；
- >500k 或 PG ANN/FTS 已调优仍不达 SLO：评估专用向量服务；
- GPU queue P95 >5s 且生成并发=1：增加 GPU/拆模型服务或选择更轻模型；
- originals >100GB/多机：迁移 S3-compatible object store；
- 需要主机故障自动恢复/RPO分钟级：再设计 PostgreSQL HA、对象存储冗余和多节点部署。
